# Web Autobattler Online

Vercel과 Neon PostgreSQL만으로 운영하는 8인 온라인 웹 오토배틀러의 사전 설계 문서입니다. 이 문서는 구현을 시작하기 전에 게임 규칙, 온라인 동기화 모델, 서버리스 제약, 데이터 구조, API, 전투 엔진, 보안, 배포 및 검증 기준을 확정하기 위한 기준점입니다.

초기 아이디어와 수치 초안은 이 README의 규칙과 구현 기준으로 통합되었습니다.

## 현재 구현 상태

도형 에셋만 사용하는 첫 플레이 가능 수직 슬라이스가 구현되어 있습니다.

- 8×8 도형 기반 2.5D 보드와 아군 4개 행 배치
- 상점 5칸, 벤치 9칸, 구매·판매·새로고침·보드 이동
- 동일 1성 유닛 3개 자동 합성
- 전사, 궁수, 기사, 마도사, 암살자 5종
- 결정론적 100ms tick 전투 엔진
- 이동, 타깃 선택, 공격 속도, 방어력, 마나, 보호막, 광역 스킬과 사망
- seed, 전체 전투 이벤트, 최종 상태와 checksum 생성
- 이벤트 시간 기반 전투 재생과 1/2/4배속
- 라운드 수입, 승패, HP 피해와 게임 종료
- Neon JSONB 상태 저장, HttpOnly 게스트 세션, `actionId` 멱등성, version 충돌 방지
- DB 연결 실패 시 현재 탭에서 계속 플레이할 수 있는 로컬 fallback

현재 온라인 범위는 **게스트 1명 대 훈련 봇의 서버 권위형 프로토타입**이다. 전투 엔진과 Neon 명령 장부를 먼저 검증하기 위한 단계이며, 8인 매칭·공유 유닛 풀·플레이어 간 pairing과 요청 기반 전체 게임 reconcile은 다음 온라인 확장 단계에서 구현한다.

### 실행

```bash
npm install
npm run dev
```

브라우저에서 `http://localhost:3000`을 연다. `.env.local`에 `DATABASE_URL` 또는 `POSTGRES_URL`이 있으면 Neon 온라인 저장 모드로 연결된다. 최초 API 요청은 `prototype_game_states`, `prototype_game_actions`와 인덱스를 idempotent하게 준비한다. 동일 SQL은 [`db/migrations/0000_prototype.sql`](./db/migrations/0000_prototype.sql)에 기록되어 있다. 현재 JSONB 프로토타입은 명시적 SQL과 Neon driver만 사용하며, Drizzle은 8인 정규화 스키마 단계까지 도입을 보류한다.

### 검증

```bash
npm test
npm run lint
npm run build
```

## 1. 목표와 전제

### 목표

- 데스크톱 웹 브라우저에서 동작하는 최대 8인 오토배틀러를 만든다.
- 상점, 경제, 유닛 구매·판매·배치, 자동 전투, 라운드 진행, 탈락 및 최종 승자를 구현한다.
- 게임 판정은 클라이언트가 아닌 서버와 DB가 소유한다.
- WebSocket이나 상시 실행 게임 서버 없이 Vercel의 요청 기반 함수와 Neon DB만으로 온라인 게임을 운영한다.
- 1~3초 정도의 상태 반영 지연과 클라이언트별 애니메이션 시차는 허용한다.
- 새로고침, 일시적인 연결 끊김, 중복 요청, 서버리스 함수 재시작에도 게임을 복구할 수 있어야 한다.

### 하지 않는 것

- 전투 중 플레이어가 프레임 단위로 개입하는 액션 게임
- 100ms마다 모든 유닛 상태를 DB에 쓰거나 모든 클라이언트에 전송하는 구조
- Vercel 함수 인스턴스의 메모리를 게임의 영구 상태로 사용하는 구조
- 정확한 실행 시점을 요구하는 초 단위 Cron 기반 게임 루프
- 첫 프로토타입 단계의 채팅, 친구, 랭크, 시즌, 결제

## 2. 게임 개요

TFT 계열의 라운드 기반 오토배틀러를 단순화한 프로토타입이다.

1. 최대 8명이 한 게임에 참가한다.
2. SHOP 단계에서 상점의 유닛을 구매하고 벤치와 보드에 배치한다.
3. 시간이 끝나면 서버가 배치를 잠그고 플레이어를 대전시킨다.
4. 서버가 전투 전체를 결정론적으로 계산하고 결과와 재생 이벤트를 저장한다.
5. 클라이언트는 저장된 이벤트를 애니메이션으로 재생한다.
6. 패자는 HP를 잃고, 생존자가 한 명이 될 때까지 반복한다.

### 기본 규칙

| 항목 | 초기값 |
| --- | --- |
| 참가 인원 | 최대 8명 |
| 초기 HP | 100 |
| 초기 레벨 | 1 |
| 최대 레벨 | 9 |
| 전체 전장 | 8×8 정사각 격자 |
| 플레이어 배치 영역 | 4×8 |
| 벤치 | 9칸 |
| 상점 | 5칸 |
| SHOP | 30초 |
| COMBAT | 최대 40초 상당의 가상 시간 |
| RESULT | 5초 |
| 상점 새로고침 | 2골드 |

게임의 상세 밸런스 수치는 DB 또는 버전 관리되는 콘텐츠 파일로 분리한다. 이 README의 숫자는 프로토타입 기준이며 코드 상수로 여러 곳에 중복하지 않는다.

## 3. 가장 중요한 아키텍처 결정

### DB는 장부이고, 실시간 게임 루프가 아니다

Neon은 다음 정보를 보관하는 단일 진실 공급원(source of truth)이다.

- 현재 게임·라운드·페이즈와 종료 시각
- 각 플레이어의 HP, 골드, 레벨, 상점, 벤치 및 보드
- 사용자가 제출한 명령과 처리 결과
- 전투 시작 시의 불변 스냅샷
- 전투 랜덤 시드, 이벤트 로그, 승패 및 피해량
- 상태 전환 버전과 감사 기록

클라이언트는 DB에 직접 접속하지 않는다. 모든 읽기와 쓰기는 Vercel API를 통하며 서버가 인증, 페이즈, 비용, 소유권과 버전을 검증한다.

### 전투는 미리 계산하고 나중에 재생한다

COMBAT 중 100ms마다 Vercel 함수를 호출하거나 DB를 갱신하지 않는다. SHOP 종료를 처음 감지한 요청이 서버에서 전투를 처음부터 끝까지 계산한다.

```text
SHOP 종료 감지
  → 배치 스냅샷 고정
  → 대전 상대와 seed 확정
  → 순수 전투 엔진으로 전체 전투 계산
  → 결과 + 시간 표시가 있는 이벤트 로그를 DB에 원자적으로 저장
  → 클라이언트가 이벤트 로그를 받아 로컬 애니메이션 재생
```

이벤트의 시간은 실제 서버 실행 시간이 아니라 전투 엔진의 가상 시간이다.

```json
{
  "seed": "round-4-pair-2-seed",
  "durationMs": 18400,
  "events": [
    { "seq": 1, "atMs": 0, "type": "MOVE", "unitId": "u1", "to": [3, 2] },
    { "seq": 2, "atMs": 700, "type": "ATTACK", "sourceId": "u1", "targetId": "u7" },
    { "seq": 3, "atMs": 800, "type": "DAMAGE", "targetId": "u7", "amount": 38 },
    { "seq": 52, "atMs": 18400, "type": "COMBAT_END", "winnerId": "p1" }
  ]
}
```

클라이언트는 `combat.startedAt`과 `atMs`를 비교하여 늦게 받은 경우 중간 시점부터 재생한다. 사용자가 탭을 다시 열었거나 전투가 이미 끝났다면 최종 상태로 빠르게 이동할 수 있다. 애니메이션의 미세한 시차는 게임 판정에 영향을 주지 않는다.

### 요청이 게임 시간을 전진시킨다

각 게임 행은 `phase`와 `phaseEndsAt`을 가진다. 상태 조회나 명령 요청이 들어올 때 서버는 먼저 `reconcileGame(gameId, now)`를 수행한다.

```text
요청 수신
  → DB 서버 시각 확인
  → phaseEndsAt이 지나지 않았으면 현재 상태 반환
  → 지났으면 게임 행 잠금
  → 아직 처리되지 않은 단계만 전진
  → 결과 커밋
  → 최신 상태 반환
```

접속자가 잠시 없으면 계산도 일어나지 않는다. 이후 첫 요청이 경과한 시각을 보고 필요한 단계를 따라잡는다. 절대적인 벽시계보다 페이즈 순서와 결과의 일관성이 중요하다.

Vercel Cron은 게임 루프로 사용하지 않는다. 향후 방치된 게임 정리, 통계 집계 등의 분 단위 유지보수에만 선택적으로 사용한다.

## 4. 상태 머신

```text
WAITING → SHOP → COMBAT → RESULT ─┬→ SHOP
                                  └→ GAME_OVER
```

| 페이즈 | 서버 책임 | 클라이언트 책임 |
| --- | --- | --- |
| WAITING | 참가, 정원 확인, 시작 조건 확정 | 대기 상태 폴링 |
| SHOP | 수입 지급, 상점 생성, 모든 명령 검증 | 구매·판매·배치, 남은 시간 표시 |
| COMBAT | 배치 잠금, 매칭, 전투 계산, 이벤트와 결과 저장 | 이벤트 다운로드 및 재생 |
| RESULT | HP 차감, 연승·연패 갱신, 탈락 판정 | 결과 표시 |
| GAME_OVER | 순위와 최종 결과 고정 | 결과 화면 표시 |

### 페이즈 전환 불변 조건

- 하나의 게임은 한 번에 하나의 페이즈만 가진다.
- `(gameId, round, phaseVersion)` 조합은 한 번만 처리된다.
- 동일 라운드·대전 쌍의 전투 결과는 하나만 존재한다.
- 서버가 저장한 전투 스냅샷은 계산 후 수정하지 않는다.
- COMBAT → RESULT 전환 시 모든 대전 결과의 HP 차감, 연승·연패, 승리 보상, 탈락과 순위를 요청자와 무관하게 **하나의 게임 단위 트랜잭션에서 일괄 적용**한다.
- 해당 라운드의 모든 `combat_jobs`가 `COMPLETED`이고 결과 checksum 검증을 통과하기 전에는 COMBAT → RESULT 전환을 허용하지 않는다. 미완료 또는 만료 작업이 있으면 요청이 계산이나 재선점을 수행한 뒤 COMBAT 상태를 반환한다.
- RESULT 적용 트랜잭션은 기대한 `(gameId, round, phaseVersion)`이 일치할 때만 성공하며, 성공과 함께 `phaseVersion`을 증가시킨다. 경쟁 요청은 0개 행 갱신 또는 새 버전을 확인하고 결과를 다시 적용하지 않는다.
- RESULT의 정산과 다음 SHOP의 수입·상점 생성은 서로 다른 전환이며 각각 정확히 한 번만 실행된다.
- 게임 종료 이후 들어온 게임 명령은 거절한다.

## 5. 온라인 동기화 모델

### 폴링

- WAITING: 2~3초 간격
- SHOP: 기본 1초, 백그라운드 탭에서는 3~5초
- COMBAT: 시작 이벤트를 받은 후 폴링을 줄이고, 종료 예정 시각에 다시 조회
- RESULT: 1초 간격 또는 결과 응답 후 다음 페이즈 시각에 조회
- 네트워크 오류: 지수 백오프와 무작위 지연(jitter), 최대 간격 제한

HTTP 캐시는 게임 상태 API에서 비활성화한다. 응답에는 `serverNow`, `stateVersion`, `phaseEndsAt`을 포함한다. 클라이언트는 `serverNow`로 로컬 시계 오차를 보정해 타이머를 표시한다.

### 명령 직후 갱신

자기 행동은 다음 폴링까지 기다리지 않는다. 구매나 배치 API 응답이 승인된 최신 플레이어 상태와 `stateVersion`을 반환하며 클라이언트 캐시에 즉시 반영한다. 낙관적 UI를 사용할 수 있지만 실패 시 반드시 서버 응답으로 되돌린다.

### 재접속

`GET /api/games/:gameId/state` 하나로 현재 페이즈, 개인 상태, 공개 상대 정보, 진행 중 전투와 최신 결과를 복원할 수 있어야 한다. 브라우저 메모리에만 존재하는 필수 상태는 두지 않는다.

### 공개 정보와 비공개 정보

- 본인에게만 공개: 현재 상점 전체, 내부 명령 오류, 인증 토큰
- 참가자에게 공개: HP, 레벨, 보드, 순위, 전투 결과
- 페이즈 종료 전 비공개를 고려할 정보: 상대의 최신 배치 스냅샷
- 서버 전용: RNG 내부 상태, 미처리 작업 정보, 토큰 해시

## 6. 동시성, 중복 요청 및 장애 복구

서버리스에서는 같은 게임에 여러 함수가 동시에 실행될 수 있다는 전제로 작성한다.

### 명령 멱등성

모든 변경 요청은 클라이언트가 생성한 UUID `actionId`를 포함한다.

- `game_actions.action_id`에 UNIQUE 제약을 둔다.
- 이미 처리된 `actionId`가 다시 오면 최초 결과를 반환한다.
- 네트워크 타임아웃 뒤 재시도해도 이중 결제나 이중 판매가 발생하지 않는다.

### 상태 버전

게임과 플레이어 상태에 증가하는 `version`을 둔다. 배치 등의 요청은 `expectedVersion`을 함께 보내며 버전이 오래되었으면 `409 CONFLICT`와 최신 상태를 반환한다.

### 원자적 처리

구매 예시:

1. action ID 중복 확인
2. 플레이어와 상점 행 잠금
3. SHOP 페이즈인지 확인
4. 골드, 빈 벤치, 판매 여부 확인
5. 골드 차감, 유닛 생성, 상점 칸 판매 처리
6. action 결과와 새 version 기록
7. 한 트랜잭션으로 커밋

핵심 상태 전환은 PostgreSQL 트랜잭션, 행 잠금(`FOR UPDATE`), UNIQUE/CHECK/외래 키 제약 및 필요 시 DB 함수로 보호한다. 애플리케이션의 사전 검사는 사용자 경험을 위한 것이며 DB 제약을 대체하지 않는다.

### 전환 작업 선점

게임 행을 잠근 뒤 `phaseVersion`을 재확인하여 한 요청만 전환 작업을 선점한다. `combat_jobs`에는 `status`, `lease_owner`, `lease_until`, `attempt_count`, `last_error`를 둔다. 초기 lease는 짧은 고정값(프로토타입 기준 10초)으로 시작하되 실제 전투 벤치마크의 p99보다 충분히 길게 조정한다.

1. 짧은 트랜잭션에서 불변 스냅샷을 만들고 작업을 `CALCULATING`으로 선점하며 `lease_until = DB_NOW + leaseDuration` 기록
2. 트랜잭션 밖에서 순수 엔진 실행
3. 결과 저장 시 `status = CALCULATING`, 자신의 `lease_owner`, 유효한 lease와 입력 checksum을 다시 확인
4. 조건이 일치할 때만 결과를 저장하고 작업을 `COMPLETED`로 변경

함수가 종료되거나 DB 연결이 끊겨 `CALCULATING`에 남더라도 `lease_until < DB_NOW`이면 다음 요청이 원자적 조건부 UPDATE로 lease를 회수한다. 이전 실행자가 뒤늦게 돌아와도 `lease_owner`가 달라 결과를 덮어쓸 수 없다. 동일 작업은 같은 엔진 버전, 입력 스냅샷, seed와 checksum을 사용하므로 재실행 결과도 같아야 한다. 반복 실패는 `attempt_count`와 `last_error`로 관측하며 일정 횟수 이후 운영 경보를 발생시키되 게임 복구 가능 상태는 유지한다.

Vercel 플랜별 함수 제한값을 게임 규칙에 하드코딩하지 않는다. 전투 계산은 제한에 근접해서는 안 되며, 타임아웃은 배포 환경 설정과 모니터링에서 별도로 관리한다.

## 7. 결정론적 전투 엔진

전투 엔진은 DB, 시스템 시각, 브라우저 API에 의존하지 않는 순수 TypeScript 패키지로 만든다.

```ts
simulateCombat({
  engineVersion,
  seed,
  boardA,
  boardB,
  contentVersion,
}): CombatResult
```

### 결정론 규칙

- `Math.random()`을 사용하지 않고 seed 기반 PRNG를 사용한다.
- 모든 유닛 처리 순서를 `nextActionAt → team → position → uid`처럼 완전히 정의한다.
- 같은 거리, 같은 HP 등 모든 동률 해소 규칙을 명시한다.
- 가능한 한 정수 또는 고정소수점 수치를 사용해 런타임별 부동소수점 차이를 줄인다.
- 엔진과 콘텐츠에 버전을 붙여 과거 전투를 그대로 재현한다.
- 이벤트에는 연속된 `seq` 번호를 부여한다.
- 무한 전투 방지를 위해 최대 가상 시간 또는 최대 tick 수를 둔다.

### 초기 전투 규칙

- 논리 tick: 100ms
- 거리: Chebyshev distance
- 타깃: 가장 가까운 적, 동률이면 현재 HP가 낮은 적, 이후 고정 tie-breaker
- 이동: 8방향 중 유효한 한 칸, 결정론적 경로 선택
- 공격 쿨다운: `floor(10 / attackSpeed)` tick
- 물리 피해: `max(1, AD × 100 / (100 + Armor))`
- 마법 피해: `max(1, AP × 100 / (100 + MagicResist))`
- 기본 공격 시 마나 +10
- 피격 시 최대 HP의 10%에 해당하는 규칙 기반 마나 획득량 적용
- 최대 마나 도달 시 스킬 사용 후 마나 초기화

### 무승부와 플레이어 피해량

- 최대 가상 시간 40초에 도달하면 `TIMEOUT_DRAW`로 종료한다.
- 같은 논리 tick에 양 팀이 모두 사망해도 `DOUBLE_KO_DRAW`로 종료한다.
- 무승부는 양쪽 모두 패배로 기록하고 양쪽 플레이어가 피해를 받는다. 이는 회복·방어 덱이 무한정 시간을 끄는 것을 막기 위한 규칙이다.
- 정상 승패에서는 패자만 피해를 받는다.
- 피해량은 `roundBaseDamage(round) + survivorStarWeight`다.
- `roundBaseDamage`: 라운드 1~2는 2, 3~4는 3, 5~6은 4, 7 이상은 5다.
- `survivorStarWeight`: 승리 팀에서 살아남은 각 유닛에 대해 1성은 1, 2성은 2, 3성은 4를 더한다.
- 타임아웃 무승부에서는 각 플레이어가 상대편 생존 유닛의 별 가중치를 기준으로 피해를 받는다. 동시 전멸이면 양쪽 모두 해당 라운드의 기본 피해만 받는다.
- 피해는 정수이며 HP는 최소 0으로 고정한다. 같은 RESULT 트랜잭션에서 피해, 탈락과 순위를 확정한다.

정확한 반올림 시점, 피격 마나의 수치 환산, 사망과 스킬 동시 처리 순서는 구현 전에 별도의 전투 규칙 테스트로 고정한다.

### 이벤트 저장 전략

프로토타입에서는 한 전투의 이벤트를 압축 가능한 JSONB 한 덩어리로 저장한다. 조회가 단순하고 쓰기 횟수가 적다. 이벤트가 커지면 요약 스냅샷과 청크 테이블로 분리한다.

전투 판정용 최종 결과와 화면 연출용 이벤트를 구분한다. 클라이언트가 이벤트 일부를 누락해도 서버의 승패와 HP 계산은 바뀌지 않는다.

## 8. 경제 및 상점

SHOP 시작 수입:

```text
earnedGold = baseIncome + interest + streakBonus + winReward
interest = min(5, floor(currentGold / 10))
```

- 기본 수입: 라운드당 5골드
- 이자: 보유 골드 10당 1, 최대 5
- 2~3 연승·연패: +1
- 4 연승·연패: +2
- 5 이상 연승·연패: +3
- 직전 전투 승리: +1

### 공유 유닛 풀

이 게임은 상대 덱을 관찰하고 같은 유닛을 두고 경쟁하는 장르적 특성을 유지하기 위해 **MVP부터 게임별 공유 유닛 풀을 사용**한다.

- `shared_unit_pools(game_id, unit_base_id, initial_count, available_count, version)`으로 재고를 관리한다.
- 상점에 유닛이 나타나는 순간 풀에서 예약 차감하고, 구매 여부와 관계없이 해당 상점 슬롯이 유지되는 동안 예약 상태로 본다.
- 상점 새로고침, 플레이어 탈락 또는 게임 종료로 슬롯이 폐기되면 풀로 반환한다.
- 플레이어 탈락 시 미구매 상점 슬롯뿐 아니라 보유한 보드·벤치 유닛도 별 등급의 원본 개수만큼 반환한다.
- 유닛 판매 시 별 등급의 원본 개수만큼 반환한다. 1성은 1개, 2성은 3개, 3성은 9개다.
- 새 상점 생성은 기존 미구매 슬롯 반환과 새 슬롯 예약을 하나의 트랜잭션으로 처리한다.
- 재고 차감은 `available_count >= requested` 조건이 있는 atomic UPDATE를 사용한다. 여러 unit row를 다룰 때는 `unit_base_id` 정렬 순서로 접근해 교착 가능성을 낮춘다.
- 재고 부족으로 선택한 유닛을 예약하지 못하면 동일한 서버 seed 스트림의 다음 후보를 시도하며, 후보 선택과 재시도 규칙도 결정론적으로 고정한다.

등급별 풀 총량과 레벨별 등장 확률은 콘텐츠 데이터로 둔다. 정확한 밸런스 값은 Phase 0 fixture에서 확정하지만 공유 풀이라는 구조 자체는 처음부터 스키마와 트랜잭션에 포함한다.

초기 콘텐츠:

| ID | 역할 | 비용 | 특징 |
| --- | --- | --- | --- |
| `U_WARRIOR` | 전사 | 1 | 근접 공격, 충전 후 강한 일격 |
| `U_ARCHER` | 궁수 | 1 | 장거리 기본 공격 |
| `U_KNIGHT` | 기사 | 2 | 높은 방어력, 보호막 스킬 |

### 자동 합성

- 같은 `baseId`와 별 등급의 유닛 3개가 모이는 즉시 다음 별 등급 1개로 합성한다.
- 구매, 이동 또는 기타 유닛 획득을 처리하는 동일 트랜잭션 안에서 연쇄 합성까지 끝낸다.
- 합성된 유닛은 소비된 세 유닛 중 하나의 UID를 canonical UID로 유지하고 나머지 둘을 제거해 장부 추적을 단순화한다.
- canonical 유닛 위치는 보드 위 후보를 우선한다. 여러 보드 후보가 있으면 `(y, x, uid)` 오름차순, 보드 후보가 없으면 `(benchSlot, uid)` 오름차순으로 선택한다.
- 구매 전 빈 벤치가 없어도 해당 구매가 즉시 합성을 완성해 최종적으로 슬롯이 필요하지 않으면 허용한다. 합성 시뮬레이션 후에도 새 유닛을 둘 자리가 없으면 `NO_SPACE`로 전체 구매를 거절하고 골드와 풀 재고를 변경하지 않는다.
- 3성은 최대 등급이며 더 합성하지 않는다.

## 9. 데이터 모델

권장 핵심 테이블은 다음과 같다. 실제 마이그레이션에서 UUID, timestamptz, integer, jsonb와 명시적 enum/check 제약을 사용한다.

### 사용자와 매칭

- `users`: 사용자 또는 익명 계정
- `sessions`: 만료되는 로그인 세션의 해시
- `matchmaking_entries`: 대기열 참가 상태와 생성 시각
- `games`: 상태, 라운드, 페이즈, 종료 시각, 버전, 콘텐츠/엔진 버전
- `game_players`: 좌석, HP, 골드, 레벨, XP, streak, 생존 상태, 순위, version

### 보유 상태

- `units`: 인스턴스 UID, 소유자, base ID, 별 등급, 위치 유형과 좌표
- `player_shops`: 라운드, 슬롯, unit base ID, 비용, 구매 여부
- `shared_unit_pools`: 게임·유닛별 초기 수량, 예약 가능한 잔여 수량과 version
- `game_actions`: action ID, 사용자, 명령 종류, payload, 처리 상태와 결과

### 전투와 복구

- `combat_jobs`: 라운드·대전 쌍, seed, 엔진 버전, 입력 checksum, 상태, `lease_owner`, `lease_until`, 시도 횟수와 오류
- `combat_snapshots`: 전투 시작 시 양쪽 보드의 불변 JSON
- `combats`: 시작 시각, 가상 지속 시간, 승자, 피해량, 최종 상태
- `combat_event_logs`: 이벤트 JSONB, checksum, schema version
- `game_events`: 페이즈 전환, 피해, 탈락 등 도메인 감사 장부

### 주요 제약

- `games`: `phase_version` 단조 증가
- `game_players`: `(game_id, seat)` UNIQUE, HP와 골드 범위 CHECK
- `units`: 보드 좌표는 소유자별 UNIQUE, 벤치 슬롯도 UNIQUE
- `player_shops`: `(game_player_id, round, slot)` UNIQUE
- `shared_unit_pools`: `(game_id, unit_base_id)` UNIQUE, `available_count >= 0` CHECK
- `game_actions`: `action_id` UNIQUE
- `combats`: `(game_id, round, pairing_index)` UNIQUE
- 모든 게임 하위 데이터는 `game_id` 외래 키로 범위를 명확히 한다.

프로토타입에서는 상태 조회 성능을 위해 정규화된 행과 함께 클라이언트용 snapshot JSON을 둘 수 있다. 단, snapshot은 파생 캐시이며 판정의 원본은 정규화된 상태와 장부다.

## 10. API 설계

모든 엔드포인트는 JSON, HTTPS, 동일 출처 쿠키 기반을 기본으로 한다.

### 세션 및 매칭

| Method | Endpoint | 역할 |
| --- | --- | --- |
| POST | `/api/session/guest` | 익명 세션 생성 |
| POST | `/api/matchmaking/join` | 대기열 참가 |
| DELETE | `/api/matchmaking/leave` | 대기열 이탈 |
| GET | `/api/matchmaking/status` | 매칭 결과 조회 |

### 상태와 명령

| Method | Endpoint | 역할 |
| --- | --- | --- |
| GET | `/api/games/:gameId/state` | reconcile 후 사용자 맞춤 상태 반환 |
| POST | `/api/games/:gameId/actions/buy` | 상점 구매 |
| POST | `/api/games/:gameId/actions/sell` | 유닛 판매 |
| POST | `/api/games/:gameId/actions/move` | 보드·벤치 이동 또는 교환 |
| POST | `/api/games/:gameId/actions/reroll` | 상점 새로고침 |
| POST | `/api/games/:gameId/actions/buy-xp` | XP 구매 |
| GET | `/api/games/:gameId/combats/:combatId` | 재생 이벤트 조회 |

변경 요청 공통 형태:

```json
{
  "actionId": "uuid",
  "expectedVersion": 17,
  "payload": {}
}
```

응답 공통 필드:

```json
{
  "serverNow": "2026-08-16T12:00:00.000Z",
  "stateVersion": 18,
  "phase": "SHOP",
  "phaseEndsAt": "2026-08-16T12:00:23.000Z",
  "data": {}
}
```

오류 코드는 `UNAUTHENTICATED`, `NOT_A_PLAYER`, `WRONG_PHASE`, `STALE_VERSION`, `INSUFFICIENT_GOLD`, `NO_SPACE`, `INVALID_POSITION`, `ACTION_ALREADY_RESOLVED`처럼 기계가 처리할 수 있게 고정한다.

## 11. 기술 스택

### 애플리케이션

- **Next.js App Router + TypeScript**: UI와 Vercel Route Handlers를 한 저장소에서 관리
- **React**: 로비, 상점, 벤치, HUD, 툴팁과 결과 UI
- **React Three Fiber + Three.js**: 2.5D 보드, 3D 유닛, 애니메이션과 전투 이펙트 렌더링
- **Drei**: 카메라, GLTF 로딩 등 검증된 React Three Fiber 보조 기능
- **Tailwind CSS**: 초기 UI 스타일링
- **TanStack Query**: 폴링, 캐시, 재시도, mutation 이후 상태 병합
- **Zod**: API 입력과 환경 변수 런타임 검증
- **Vitest**: 순수 게임 규칙과 API 단위 테스트
- **Playwright**: 다중 브라우저 게임 흐름 E2E 테스트

### 데이터

- **Neon PostgreSQL**: 영속 상태, 트랜잭션, 잠금 및 장부
- **Drizzle ORM + drizzle-kit**: 타입 안전 쿼리와 SQL 마이그레이션
- **`@neondatabase/serverless`**: Vercel에서 Neon 연결
- 중요 트랜잭션은 Drizzle에만 추상화하지 않고 SQL과 제약조건을 명시적으로 검토

### 배포와 운영

- **Vercel**: Next.js 배포와 요청 기반 함수
- Vercel 함수와 Neon primary compute를 가능한 한 가까운 리전에 배치
- Vercel Preview는 별도의 Neon branch 또는 별도 DATABASE_URL 사용
- GitHub Actions 또는 Vercel 빌드 전 단계에서 lint, typecheck, unit test 실행
- 구조화 JSON 로그에 `requestId`, `gameId`, `playerId`, `actionId`, `phaseVersion` 포함

Redis, 메시지 큐, 별도 WebSocket 서버는 초기 필수 스택에 포함하지 않는다. 실제 부하 측정 후 매칭 또는 캐시 병목이 확인될 때만 추가한다.

### 2.5D 렌더링 결정

게임 화면은 롤토체스처럼 고정된 대각선 시점에서 3D 캐릭터가 격자 보드 위를 이동하는 2.5D 방식으로 구현한다. 판정은 순수 TypeScript 8×8 격자 엔진이 담당하고, React Three Fiber/Three.js는 서버가 확정한 전투 이벤트만 재생한다. 로비, 상점, 벤치, HUD와 결과창은 HTML/React로 유지한다.

좌표계, 이벤트 재생, GLB 에셋 계약, 애니메이션 상태 머신, 성능 예산, GPU 리소스 생명주기와 구현 완료 기준은 [`docs/2_5D_RENDERING_ARCHITECTURE.md`](./docs/2_5D_RENDERING_ARCHITECTURE.md)를 따른다.

## 12. 서버리스 구현 원칙

- 함수 인스턴스의 전역 변수는 성능 캐시로만 보고 정확성에 사용하지 않는다.
- 각 요청은 독립적으로 재실행 가능해야 한다.
- 함수가 응답한 뒤 실행될 것이라고 가정한 작업에 필수 판정을 맡기지 않는다.
- DB 연결은 요청 범위에서 관리하고 장시간 유지하지 않는다.
- 모든 시간 판정은 클라이언트 시간이 아니라 DB 또는 서버 시간을 사용한다.
- 큰 전투 로그는 상태 API에 매번 포함하지 않고 combat endpoint에서 한 번 가져온 뒤 캐시한다.
- 한 번의 폴링에서 전체 게임 행을 매번 내려주지 않고 사용자에게 필요한 스냅샷만 반환한다.
- 정적 콘텐츠는 배포 자산 또는 버전된 데이터로 캐시하고, 진행 중 게임은 시작 당시 content version을 고정한다.

### 서버리스에서도 가능한 이유

게임이 상시 실행되는 프로세스를 필요로 하지 않기 때문이다. SHOP은 종료 시각이 있는 저장 상태이고, COMBAT는 동일 입력으로 다시 만들 수 있는 유한 계산이며, RESULT는 한 번만 적용되는 트랜잭션이다. 프로세스가 사라져도 DB의 스냅샷, seed, 작업 상태와 장부만 있으면 다음 요청이 이어서 처리할 수 있다.

## 13. 인증과 보안

- 초기에는 게스트 계정을 지원하되 서버가 발급한 충분히 긴 무작위 세션을 `HttpOnly`, `Secure`, `SameSite=Lax` 쿠키에 저장한다.
- DB에는 원본 세션 토큰이 아니라 해시와 만료 시각을 저장한다.
- 모든 명령에서 세션 사용자와 game player 소유권을 다시 확인한다.
- 클라이언트가 보낸 비용, 스탯, 피해, 승자, 현재 페이즈를 신뢰하지 않는다.
- Zod로 payload 크기와 좌표·문자열 범위를 제한한다.
- origin/CSRF 방어, 요청 body 제한, 사용자·게임별 rate limit을 적용한다.
- 로그에 쿠키, 토큰, DATABASE_URL 또는 전체 비공개 상태를 남기지 않는다.
- 관리자용 DB 자격 증명은 서버 환경 변수에만 두고 `NEXT_PUBLIC_` 변수로 노출하지 않는다.
- 개발/미리보기/운영 DB와 자격 증명을 분리한다.

## 14. 성능 및 비용 전략

가장 피해야 할 비용은 8명이 100ms마다 상태를 읽고 모든 유닛을 쓰는 구조다. 기본 1초 폴링도 게임당 초당 최대 약 8회 읽기이므로 응답을 작게 하고 인덱스를 갖춰야 한다.

- 상태 변경이 없으면 `stateVersion` 기반의 작은 응답 사용
- 전투 이벤트는 한 번 다운로드 후 브라우저 캐시
- 게임별 조회는 항상 `game_id`와 필요한 인덱스로 제한
- 종료 게임은 일정 기간 후 hot table에서 보관용 테이블 또는 축약 결과로 정리
- 폴링 간격은 페이즈와 탭 visibility에 따라 조절
- 게임 함수와 DB 리전을 가깝게 배치해 왕복 지연 축소
- 실제 쿼리 수, 함수 호출 수, 평균 응답 크기, 전투 계산 시간을 계측한 뒤 최적화

초기 목표치는 다음과 같다.

| 지표 | 목표 |
| --- | --- |
| 명령 API p95 | 같은 리전 기준 500ms 이내 |
| 상태 반영 | 정상 네트워크에서 2초 이내 |
| 전투 계산 p95 | 500ms 이내 |
| 상태 응답 | gzip 전 수십 KB 이하 |
| 전투 이벤트 | 일반 전투 수백 KB 이하 |
| 중복 명령 | 결과 변화 0회 |

이 값들은 출시 보장이 아니라 프로토타입 부하 테스트 기준이다.

전투 계산은 더 엄격하게 **1대1 전투 평균 10ms, p95 50ms 이내**, 8인 한 라운드의 4개 전투 합계 p95 250ms 이내를 구현 목표로 둔다. 우선 단일 함수의 가벼운 동기 루프로 계산하고 측정한다. CPU-bound TypeScript 작업을 `Promise.all`로 감싸는 것은 실제 CPU 병렬화를 보장하지 않는다. 측정 결과가 목표를 넘을 때만 Worker 분리, 작업 분할 또는 엔진 최적화를 검토하며, 네 전투를 별도 서버리스 요청으로 무조건 분산해 네트워크·복구 복잡도를 늘리지 않는다.

## 15. 테스트 전략

### 단위 및 속성 테스트

- 같은 입력과 seed가 항상 동일한 checksum과 결과를 만드는지 검사
- 타깃 선택, 이동 tie-breaker, 공격 속도, 방어 공식, 마나, 스킬, 사망 순서
- 빈 보드, 동시 사망, 이동 불가, 최대 tick 도달
- 경제, 이자, 연승·연패, 레벨 및 합성
- 임의 보드에 대해 HP 음수, 중복 위치, 살아난 사망 유닛 같은 불변식 위반 검사

### DB 통합 테스트

- 같은 `actionId`를 동시에 여러 번 보내도 한 번만 처리
- 마지막 골드로 동시에 구매했을 때 하나만 성공
- 여러 요청이 만료 페이즈를 동시에 발견해도 한 번만 전환
- 전투 작업 도중 실패 후 같은 seed로 복구
- lease 만료 후 다른 요청이 작업을 회수하고, 늦게 끝난 이전 소유자는 결과를 덮어쓰지 못함
- RESULT 재시도 시 HP가 두 번 차감되지 않음
- 8개 경쟁 요청에서도 모든 플레이어의 HP·streak·탈락이 한 번의 RESULT batch로만 변경됨
- 오래된 version의 배치 요청이 최신 배치를 덮어쓰지 않음
- 동시 상점 갱신·구매·판매 후 공유 풀 총량 보존

### E2E 테스트

- 8개 브라우저 context로 매칭부터 게임 종료까지 실행
- 느린 네트워크, 응답 순서 뒤바뀜, 중복 클릭, 탭 새로고침
- SHOP 종료 경계에서 구매 요청
- 전투 중 재접속과 이미 끝난 전투 복원
- 한 플레이어가 장시간 응답하지 않아도 나머지가 진행 가능

### 부하 테스트

- 동시 게임 수별 폴링 QPS
- Neon 연결 수와 쿼리 지연
- reconcile 경합과 잠금 대기
- 전투 로그 크기 및 다운로드 비용
- cold start가 명령과 상태 조회에 미치는 영향

## 16. 관측성과 운영

다음 지표를 수집한다.

- API별 요청 수, 오류율, p50/p95/p99 지연
- 폴링당 DB 쿼리 수와 전송 바이트
- 페이즈 전환 지연(`processedAt - phaseEndsAt`)
- 전투 계산 시간, tick 수, 이벤트 수와 checksum 불일치
- DB deadlock, serialization failure, connection error
- 멱등성 중복 감지 수와 stale version 충돌 수
- 진행이 멈춘 `CALCULATING` 작업과 비정상적으로 오래된 게임 수

오류 응답과 로그는 공통 `requestId`로 연결한다. 운영 도구는 게임 ID로 현재 상태, phase version, 최근 actions, combat job을 읽을 수 있어야 하지만 임의 상태 수정 기능은 초기에는 두지 않는다.

## 18. 구현 전 확정할 제품 결정

### Phase 0에서 확정된 결정

- 공유 유닛 풀을 MVP부터 사용한다.
- 홀수 생존자에게는 다른 생존자의 현재 라운드 잠금 배치 스냅샷을 복제한 유령을 배정한다.
- 유령의 원본 플레이어는 자신의 실제 대전 결과 외에 유령 대전으로 피해나 추가 보상을 받지 않는다.
- 유령을 상대하는 플레이어가 이기면 유령 원본에게 피해를 주지 않지만 정상적인 승리 결과와 승리 보상을 얻는다.
- 유령을 상대하는 플레이어가 지면 본인만 일반 공식의 피해를 받고 패배 streak가 적용된다.
- 유령과의 무승부도 실제 플레이어에게만 무승부 피해를 적용한다.
- 유령 원본은 해당 실제 플레이어 자신이 될 수 없으며, 직전 유령 원본 반복을 가능한 한 피한다. 선택 동률은 round seed와 player ID로 결정론적으로 해소한다.
- 패배 피해량, 무승부 및 자동 합성 규칙은 각각 7절과 8절의 공식을 따른다.

### 아직 확정할 제품 결정

다음 항목은 Phase 0에서 추가로 결정한다.

- 8명이 모여야 시작할지, 제한 시간 후 봇 또는 소수 인원으로 시작할지
- 대전 상대 반복 방지 규칙
- 상점 잠금, XP 구매, 아이템, 시너지의 초기 포함 여부
- 연결이 끊긴 플레이어의 자동 진행 및 기권 시점
- 전투 이벤트 공개 범위와 관전 허용 여부

초기 MVP는 봇 없이 2명부터 시작 가능한 개발 모드와, 독립 상점, 아이템·시너지 없음, 자동 합성만 포함하는 구성이 가장 빠르게 핵심 구조를 검증한다.

## 19. 최종 기술 판단

이 게임은 Vercel과 Neon만으로 구현 가능하다. 성공 조건은 WebSocket의 동작을 DB 폴링으로 그대로 흉내 내는 것이 아니라 다음 세 원칙을 지키는 것이다.

1. **서버와 DB가 판정을 소유하고 클라이언트는 명령과 표현만 담당한다.**
2. **페이즈는 종료 시각이 있는 영속 상태이며, 요청이 들어올 때 멱등적으로 전진한다.**
3. **전투는 결정론적으로 한 번 계산해 결과와 이벤트를 저장하고, 클라이언트는 비동기적으로 재생한다.**

이 구조에서는 지연이나 함수 재시작이 화면의 시작 시점을 늦출 수는 있어도 게임 결과를 바꾸지 않는다. 따라서 완전한 실시간 인프라 없이도 공정하고 복구 가능한 온라인 오토배틀러를 만들 수 있다.
